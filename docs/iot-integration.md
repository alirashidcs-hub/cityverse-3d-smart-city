# CityVerse — IoT & External Data Integration

## Goal

Everything in the prototype is demo/simulated data generated by a seeded
PRNG. The architecture is built so that swapping in real sensor feeds later
requires **no changes to the frontend** — only to what populates the
`traffic_samples` / `energy_readings` / `air_quality_samples` / etc. tables.
The UI always reads from the same `/api/*/current` endpoints regardless of
whether the underlying row came from a sensor or the demo generator.

## Sensor types & ingestion paths

| Sensor type | Typical protocol | Ingest path |
|---|---|---|
| Traffic loop detectors / cameras | HTTP webhook or vendor API poll | `POST /api/ingest/traffic` |
| Air quality stations | MQTT (e.g. AWS IoT Core, HiveMQ) | MQTT → ingestion worker → Postgres |
| Smart electricity meters | MQTT or vendor REST API | ingestion worker (batched, every 1–5 min) |
| Water flow / pressure sensors | MQTT or Modbus-to-HTTP gateway | ingestion worker |
| Weather stations | Public API (NOAA, OpenWeather) or on-site station | Scheduled poll every 5–10 min |
| Public transport (GTFS-realtime) | GTFS-RT feed (protobuf over HTTP) | Scheduled poll every 30s |

## Ingestion gateway

```
[ Sensors / vendor APIs / GTFS-RT ]
              │
              ▼
   Ingestion Gateway (small Node/Go service, not a Vercel function —
   needs a persistent MQTT connection)
              │  - validates payload against a JSON schema per sensor type
              │  - normalizes units (kWh, m³, µg/m³, kph)
              │  - maps vendor device id → sensors.external_ref
              │  - discards/flags out-of-range values
              ▼
        Postgres (via connection pool / pgbouncer)
              │
              ▼
   Realtime layer (Supabase Realtime channel) pushes deltas to
   any connected browser tabs — the 3D city updates roads/overlays
   live without a page refresh.
```

## Normalized message schema (internal, post-ingestion)

```json
{
  "sensorId": "uuid",
  "kind": "traffic_loop",
  "capturedAt": "2026-08-13T10:15:00Z",
  "value": { "level": 0.62, "avgSpeedKph": 28 },
  "source": "sensor",
  "quality": "ok"
}
```

`quality` can be `ok`, `stale`, or `suspect` (e.g. value outside physically
plausible range) — the API layer treats `suspect` readings as absent and
falls back to the demo model for that entity until a healthy reading arrives.

## Handling sensor gaps

- `sensors.last_seen_at` drives a simple health check: if no reading in
  `> 2×` the sensor's expected interval, `sensors.status` flips to `offline`
  and `/api/*/current` silently falls back to the parametric demo generator
  for that road/building/district — the frontend never has to know which
  mode it's in.
- A `Data source` indicator (small badge, not yet built) can later show
  "Live" vs "Simulated" per layer so operators know what they're looking at.

## Mapping sensors onto the 3D city

Each `sensors` row carries `x, z` (or a `road_id`/`building_id` reference).
The renderer already keys roads/buildings by array index matching
`cityData.roads` / `cityData.buildings` — in production this becomes a
lookup by `id` returned from `/api/city/graph`, so a sensor reading updates
exactly the road segment or building it's attached to, not an approximation.

## GIS / external map data

For a production deployment tied to a real city, `buildings` and `roads`
would be seeded from OpenStreetMap or municipal GIS (shapefiles/GeoJSON)
via the admin import pipeline (`api-design.md` → `/api/admin/import`),
rather than the procedural generator — the generator remains useful for
demos, sales, and testing.

## Rate & volume expectations (planning numbers)

For a mid-size city pilot (~500 sensors, 1 reading/min average):
~720,000 rows/day across time-series tables. Well within Postgres/Supabase
limits with the partitioning strategy in `database-schema.md`; revisit
if scaling to metro-wide sensor density (tens of thousands of devices).
